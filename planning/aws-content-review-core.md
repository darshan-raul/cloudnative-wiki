# AWS core content review

Reviewed 2026-10-12. Scope: 46 notes, including `content/AWS.md`. This is a body/teaching review, not a test result. Current bodies were read and original notes compared against Git HEAD, not the staged trimmed versions. New notes have no HEAD original. No content, index, commit or AWS resource was changed by this review.

## Findings

### K1 — P2: Auto Scaling refresh exercise omits the configuration transition

`content/AWS/compute/auto-scaling.md:29–32` creates a group on a fixed template version, creates another version, then instructs starting a refresh and proving rollback/abort. Creating a template version alone does not select it for the group/refresh. Without an explicit desired configuration the exercise can refresh instances onto the old version. It also leaves cancellation and rollback indistinguishable.

Restore a worked group/target-tracking/refresh example with numeric template versions, `DesiredConfiguration`, warm-up/health settings, checkpoints and expected results. Explain that cancelling stops further replacements rather than restoring already-replaced instances. Rollback has configuration prerequisites and is not automatic merely because the marker is unhealthy. The original EC2 note had group/scaling commands; moving the topic to this new page has not supplied equivalent practical depth. The EC2 page calls the link a full exercise, which overstates its present completeness.

Sources: [starting a refresh](https://docs.aws.amazon.com/autoscaling/ec2/userguide/start-instance-refresh.html), [rollback prerequisites and behavior](https://docs.aws.amazon.com/autoscaling/ec2/userguide/instance-refresh-rollback.html). Confidence: high; incomplete executable workflow, not a claim that every outline is factually wrong.

### K2 — P2: Route 53 lost valid record and health-check coverage

`content/AWS/networking/dns/README.md:47–58` retains A/AAAA, CNAME and alias plus routing policies. The original HEAD note's **DNS Record Types** table also explained MX, TXT, NS, SOA, PTR, SRV and CAA. These useful mail/verification/delegation/reverse-lookup/service/certificate distinctions were removed, not corrected or routed to an equivalent AWS-specific explanation.

The original **Health Check Types** section distinguished endpoint, calculated and CloudWatch-alarm checks. The current generic health caveats do not teach that choice. Restore the distinctions while correcting original inaccurate checker/threshold claims. In particular, internet endpoint checks cannot directly probe private IP endpoints; calculated checks combine child results; alarm-based checks evaluate the alarm data stream rather than simply waiting for its ALARM state.

Sources: [record types](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/ResourceRecordTypes.html), [health-check types](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-types.html), [health-check configuration](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-creating-values.html). Confidence: high, confirmed original-topic loss.

### K3 — P2: ELB lost cross-zone and session-affinity explanations

`content/AWS/networking/load-balancing/README.md:13–70` now explains protocols, health, SGs and draining, but contains no cross-zone or sticky-session explanation. HEAD had separate **Cross-Zone Load Balancing** and **Sticky Sessions** sections with useful operational examples. Their absence leaves target distribution and stateful-session trade-offs unexplained.

Restore ALB/NLB cross-zone defaults and supported target-group overrides, an uneven-AZ target example, and ALB duration/application-cookie affinity with its limitations. Explain that affinity does not make in-memory state durable, and distinguish target-group selection stickiness from target affinity in weighted forwarding. Do not restore original inaccurate protocol/quota/cost universals along with these valid topics.

Sources: [ALB target-group attributes](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html), [NLB target-group attributes](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/edit-target-group-attributes.html), [forward action behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/rule-action-types.html). Confidence: high, confirmed original-topic loss.

### K4 — P2: IAM exception is named but not taught with an answer

`content/AWS/security/iam/policy-evaluation.md:42` asks learners to predict role-ARN versus role-session-ARN grants with a boundary omitting the action, then sends them to external documentation. The body warns about the distinction but gives neither fixture nor worked outcome.

Add an explicitly same-account example with full policy documents and a result table: a resource grant to a role ARN remains constrained by implicit permissions-boundary denial; a direct role-session-ARN grant is not constrained by that implicit denial. Applicable explicit denies still win. State identity/session/organization assumptions and keep cross-account/KMS cases separate. This is missing teaching depth, not a false claim that the existing caution is wrong.

Source: [principal-specific permissions-boundary rules](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html). Confidence: high.

### K5 — P2: First-session handoff promises role creation not supplied by its lab

`content/AWS/foundations/getting-started.md:49` calls the Lambda lab complete and instructs creating the dedicated execution role and log group. `content/AWS/compute/lambda/README.md:28` instead requires an existing role trusting Lambda and having log permissions. Its function-creation commands do not create that role. The IAM role exercise's LabCaller trust is not a Lambda execution-role substitute.

Either provide the dedicated Lambda role/log-group workflow, including restricted logging policy, PassRole prerequisites, verification and dependency-ordered cleanup, or explicitly require an administrator-provided role and narrow the first-session promise accordingly. A valid prerequisite-based function example is not by itself a complete beginner deployment path.

Sources: [CreateFunction requires an execution role](https://docs.aws.amazon.com/lambda/latest/api/API_CreateFunction.html), [execution-role setup](https://docs.aws.amazon.com/lambda/latest/dg/lambda-intro-execution-role.html). Confidence: high for the handoff mismatch.

### K6 — P2: Delivery-pipeline exercise still lacks a worked artifact/deploy contract

`content/AWS/developer-tools/README.md:23–27` asks for a test, build specification, pipeline and deployment, without a sample application/buildspec, named deployment target, artifact layout or stage configuration. The existing EKS link can support that specific target but does not provide the claimed generic sandbox workflow within this page.

Supply a small deterministic application and version 0.2 buildspec, then one supported target's artifact/stage/role handoff, passing/failing evidence and rollback. Alternatively label this explicitly as a design exercise with external implementation prerequisites. Do not claim the outline has been exercised on AWS.

Sources: [buildspec contract](https://docs.aws.amazon.com/codebuild/latest/userguide/build-spec-ref.html), [CodeBuild getting-started workflow](https://docs.aws.amazon.com/codebuild/latest/userguide/getting-started-overview.html). Confidence: high as a bounded learning-depth gap, not an API error.

### K7 — P2: Backup restore drill is resource-agnostic where implementation is not

`content/AWS/reliability/backup-and-recovery.md:23–31` proposes restoring an unspecified resource. It supplies no resource-specific restore metadata, concrete recovery-point/role inputs or expected service checkpoints. The general safety advice is good, but it cannot stand in for a worked restore.

Add one explicit supported resource, such as a disposable EBS volume: source marker, recovery-point identification, retrieved/overridden restore metadata, destination AZ/type, restore role/job, newly restored volume verification and retained-copy cleanup. Keep the general feature matrix and RTO/RPO interpretation rather than pretending this example applies unchanged to all services.

Sources: [EBS restoration](https://docs.aws.amazon.com/aws-backup/latest/devguide/restoring-ebs.html), [StartRestoreJob metadata contract](https://docs.aws.amazon.com/aws-backup/latest/APIReference/API_StartRestoreJob.html). Confidence: high as a learning-depth gap.
