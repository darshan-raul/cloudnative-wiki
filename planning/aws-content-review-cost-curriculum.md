# Independent content review: AWS cost and SAP curriculum

Review date: 2026-10-12. Scope: **46 pages**—twenty cost-management notes, the concepts/cost-management view, and twenty-five SAP-C02 pages (twenty tasks, four domain hubs and the overview). This reviewer did not author their current remediation.

This is a **content review**, not a build/test report. Every current body was read; HEAD originals and topic structure were compared using git show HEAD:path, independently of staged/index state. Consequential claims were checked against owning AWS documentation. Old audit/progress ledgers were not treated as proof. No content, Git index or AWS resources were changed.

## Findings and confidence

Two confirmed technical corrections and one confirmed learning-depth regression remain in the reviewed snapshot. The rest of this report distinguishes specific independently checked improvements from uncertainty; absence of another finding is not a certification of every sentence, Region, service configuration or proposed lab.

### C1 — P2: EFS lifecycle exercise implies unsupported prefix-scoped policy

**Current evidence:** [efs-cost-optimization.md:63](../content/AWS/cost-management/efs-cost-optimization.md:63) proposes selecting a lifecycle policy for “one prefix/application population.” The exercise presents this as a way to isolate the candidate policy on an existing filesystem.

**HEAD evidence:** The original note's lines 31–38 prescribed filesystem lifecycle unconditionally. That was overly broad, but did not establish any prefix-filter mechanism. The current prefix-scoped suggestion is a new unsupported scoping assumption, not a valid recovery of an original capability.

**Why it matters:** EFS lifecycle configuration operates on the whole filesystem, with no S3-style prefix filter. If the learner applies the proposed policy to a shared filesystem, other applications' files are also subject to its transitions. This contradicts the intended bounded/rollback-safe experiment.

**Owning evidence:** [EFS lifecycle behavior](https://docs.aws.amazon.com/efs/latest/ug/lifecycle-management-efs.html) explicitly defines filesystem-wide application; [PutLifecycleConfiguration](https://docs.aws.amazon.com/efs/latest/APIReference/API_PutLifecycleConfiguration.html) accepts the filesystem ID and lifecycle transitions, not a prefix or application selector.

**Proposed fix:** Use a disposable filesystem containing the selected representative application population, or evaluate the entire existing filesystem's populations before proposing a change. State that filesystems, not prefixes, are the lifecycle-policy boundary. Preserve the useful size/access/cost benchmark and rollback work. Confidence: **high**.

### C2 — P2: S3 RTC design target is presented as the SLA threshold

**Current evidence:** [s3-cost-optimization.md:42](../content/AWS/cost-management/s3-cost-optimization.md:42) calls 99.99% within 15 minutes a documented SLA. Line71 correctly rejects an every-object guarantee, but does not correct the SLA percentage.

**HEAD evidence:** Original line 91 claimed replication was guaranteed within 15 minutes for objects without qualification. The current text improves that blanket guarantee but replaces it with an incorrect contractual percentage.

**Why it matters:** An engineering/design target and the contractual monthly credit threshold are different. Learners can choose the wrong recovery/risk assumption or wrongly expect a service credit between 99.9% and 99.99%.

**Owning evidence:** [The RTC SLA](https://aws.amazon.com/s3/sla-rtc/) applies monthly per region pair/account and starts service credits below 99.9%; [AWS replication features](https://aws.amazon.com/s3/features/replication/) describes that 99.9% SLA. [The S3 FAQ](https://aws.amazon.com/s3/faqs/) distinguishes the 99.99% design target from the 99.9% credit trigger.

**Proposed fix:** Describe the 99.99% design goal separately, and use 99.9% for the monthly SLA threshold with eligibility/exclusions and per-region-pair scope. Keep the warning that neither figure guarantees every object or an application's exact RPO. Confidence: **high**.

### C3 — P3: Valid Elastic Beanstalk comparison disappeared with retired OpsWorks guidance

**Current evidence:** [2.1-deployment-strategy.md:27](../content/AWS/solutions-architect-professional/domain-2/2.1-deployment-strategy.md:27), its component table at lines 29–39 and configuration discussion at line 52 replace OpsWorks with generic supported-tool advice. Elastic Beanstalk is not named in that lesson or an equivalent scoped deployment comparison. The SAP overview's compute map also omits it, though that map correctly says it is representative.

**HEAD evidence:** Original task 2.1 line 53 separately distinguished Beanstalk managed app deployment from Systems Manager fleet operations. That remained a valid concept even though the same callout's OpsWorks recommendation became obsolete.

**Why it matters:** Removing retired-service advice should not erase a supported managed deployment alternative. The lesson retains IaC/pipelines/fleet tooling but no longer helps a learner contrast them with application-platform deployment. This is a loss of valid original learning depth, not a claim that every in-scope AWS service must be taught exhaustively.

**Owning evidence:** [Elastic Beanstalk's guide](https://docs.aws.amazon.com/elasticbeanstalk/latest/dg/Welcome.html) describes managed application deployment/provisioning/health/scaling, with current Standard/Cluster mode distinctions; [the SAP-C02 in-scope list](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-professional-02/sap-02-in-scope-services.html) still includes it. [Official task 2.1](https://docs.aws.amazon.com/aws-certification/latest/solutions-architect-professional-02/solutions-architect-professional-02-domain2.html) includes adopting managed services to reduce provisioning/patching overhead.

**Proposed fix:** Restore a compact sourced row/paragraph contrasting supported Beanstalk application deployment with IaC/pipeline orchestration and Systems Manager node operations, including platform/version responsibilities and underlying-resource cost. Do not revive Chef/Puppet OpsWorks as active guidance or make one old PaaS slogan universal across current modes. Confidence: **high for the loss**, editorial priority **P3**.

## Uncertainty and teaching limitations

1. **Supplied-data drills are not uniformly self-contained.** For example, task 4.1 asks for six supplied application profiles; task 1.5 asks for a supplied billing extract. Those inputs are not in the respective bodies. The reader can use an external classroom dataset or authorized environment, but a self-study reader needs sample inputs/expected decision criteria or a clear link. This is a usability limitation, not an assertion that the conceptual scenario is wrong or that every revision page must become a runnable tutorial. CUR's actual local fixture is a positive exception.
2. **Gross/net savings need explicit before/after accounting.** The 3.5 example subtracting unused commitment from gross avoidance can be valid under its stated assumptions, but the 300/180/20 figures do not establish the actual source bill or alternative benefit use. Treat it as a simplified exercise; a real recommendation needs a per-hour before/after ledger to avoid double-counting sunk payments. No confirmed numeric error is claimed.
3. **Local execution provenance is not re-proved here.** CUR says its fixture was run in an in-memory engine. The query/results are internally coherent, but this review did not rerun it or treat prior execution/test claims as evidence of AWS behavior.
4. **Eligibility details remain configuration-dependent.** Marketplace seller restrictions, Database SP service/generation/usage eligibility, Free Tier cohorts/Organizations effects, certificate/placement rules, endpoint pricing exceptions and source-specific migration prerequisites require the selected actual account/Region/product. The notes often say this appropriately; this review does not certify every combination.
5. **Broader API/policy/lab semantics were read, not live exercised.** The read-only inventory/query requests have plausible correctly scoped contracts; the proposed SCP and deployment/failover drills are explicitly not claimed as production deployments. No success on a parser/build was used to conclude authorization, safety or application correctness.
