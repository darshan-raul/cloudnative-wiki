# AWS operations content review

Reviewed 2026-10-12. This is an independent semantic and teaching review of **39 current notes**, not a test/build report. All current bodies were read, including the two new notes. The comparison baseline was `HEAD`, not the Git index; original headings/topic coverage and relevant original prose/examples were compared with the working versions. Original examples were sampled for contract and educational equivalence, not executed or exhaustively API-certified. The entire IAM subtree is excluded by assignment.

Four confirmed defects remain in the reviewed snapshot. There is one lower-confidence cleanup ambiguity. No other consequential factual defect or useful-original-topic loss without an equivalent was established in this pass. This is not certification of every AWS claim, price, quota, IAM permission, or runnable deployment. Labs were evaluated by their stated prerequisites, actions, observable evidence, failure cases, and cleanup—not by whether the site builds.

## Confirmed findings

### OPS-01 — P2: invalid daily scheduled-rule expression

- Current: `content/AWS/monitoring/cloudwatch-events/README.md:47` gives `cron(0 9 \* _ ? _)` as 09:00 UTC daily. The month and year underscores are invalid, and the example is not protected as inline code.
- Original: `HEAD:content/AWS/monitoring/cloudwatch-events/README.md:82` had the valid inline-code expression `cron(0 10 * * ? *)` for daily 10:00 UTC. This is a restoration/formatting regression, not an intentionally removed obsolete API.
- Reason: legacy EventBridge scheduled rules use six cron fields; the wildcard is `*`, not `_`. Copying the current expression fails the contract. AWS's [scheduled-rule syntax and examples](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-scheduled-rule-pattern.html) own this contract.
- Proposed fix: write inline code `cron(0 9 * * ? *)`; also format `rate(5 minutes)` as code. Retain the distinction between legacy UTC rules and Scheduler timezone/flexible-window behavior.
- Confidence: high.

### OPS-02 — P2: SQS partial-batch handler fails the entire batch for non-object JSON

- Current: `content/AWS/application-integration/sqs/README.md:123` calls `body.get("eventId")`; line 125 catches only `ValueError` and `TypeError`. Valid JSON bodies such as `[]`, `null`, `42`, or a quoted string deserialize to non-dictionaries and raise an uncaught `AttributeError`. The claimed individual-failure behavior is therefore false for common invalid envelopes.
- Original: the HEAD Lambda example simply deserialized/logged each record, without the new partial-batch validation contract. Do not restore that weaker original handler; repair the useful new example.
- Reason: [Lambda's SQS partial-batch error contract](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html) explicitly treats an uncaught function exception as failure of the entire batch. Successfully processed records can then be retried. This conclusion follows directly from the shown Python control flow, not a test run.
- Proposed fix: validate `isinstance(body, dict)` before `.get`, then validate the field. Keep failures inside the per-record handling boundary. Teach a mixed batch containing a valid object, malformed JSON, and valid non-object JSON; only invalid records should appear in `batchItemFailures`. Keep the existing distinction between standard-queue handling and FIFO stop-after-first-failure behavior.
- Confidence: high.

### OPS-03 — P2: WebSocket cost scenario implies impossible connection lifetimes

- Current: `content/AWS/serverless/api-gateway/README.md:60` models “10,000 WebSocket connections lasting a full 30 days.” API Gateway closes an individual WebSocket connection after at most two hours; the idle timeout is ten minutes.
- Original: `HEAD:content/AWS/serverless/api-gateway/README.md:278` similarly described “10K always-open connections,” and also had an incorrect monthly total. The current arithmetic is repaired, but the underlying lifetime model is not.
- Reason: the owning [WebSocket quotas table](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-execution-service-websocket-limits-table.html) makes these duration limits non-adjustable. The cost arithmetic can describe an average concurrent population sustained through reconnects, not the same connections surviving thirty days.
- Proposed fix: describe an average of 10,000 concurrent active connections throughout a 30-day period, with reconnects within the two-hour maximum and activity within the idle timeout. Preserve `10,000 × 43,200 = 432 million` connection-minutes and the explicitly hypothetical rate/total. Add reconnect/new-connection-ID implications to the existing connection registry, authentication, TTL and `GoneException` operations discussion.
- Confidence: high.

### OPS-04 — P3: GuardDuty description preserves the fabricated Enterprise tier

- Current: `content/AWS/security/guardduty/README.md:3` still advertises “GuardDuty Enterprise.” Its own line 17 correctly says there is no Enterprise tier, and line 80 rejects the fabricated configuration.
- Original: the same description and a `GuardDuty Enterprise` section existed in HEAD; the body was corrected but the description was overlooked.
- Reason: the frontmatter appears in site/search summaries and contradicts the lesson. AWS's [GuardDuty feature/protection-plan catalogue](https://docs.aws.amazon.com/guardduty/latest/ug/what-is-guardduty.html) describes foundational detection, protection plans and organization management, not this named tier.
- Proposed fix: replace that description fragment with current protection plans and organization/delegated-administrator operations. Do not reintroduce the old invented Enterprise API.
- Confidence: high (especially the direct internal contradiction).

## Uncertain item / clarification rather than a confirmed defect

### OPS-U01 — Macie cleanup wording could imply deleting a cloud job

`content/AWS/security/macie/README.md:30` says to remove the disposable “job configuration/fixture/bucket.” This may mean removing the local request configuration file, but it could be read as deleting the Macie job. Line 108 gives the more appropriate documented cancel/cleanup workflow. The [Classification Job API resource](https://docs.aws.amazon.com/macie/latest/APIReference/jobs-jobid.html) exposes describe and status update operations; the [job status lifecycle](https://docs.aws.amazon.com/macie/latest/user/discovery-jobs-status-change.html) documents pause/resume/cancel, not a job-delete operation. The phrase does not explicitly name a nonexistent API, so it is **not counted as a confirmed API defect**.

Proposed clarification: cancel remaining running lab work using the supported lifecycle; remove local request files and synthetic S3 fixtures/results as appropriate; restore prior discovery settings. Do not promise deletion of retained job metadata or disable shared organization protection. Confidence: medium that readers could misinterpret the present cleanup sentence; high on the supported status-change contract.

## Source-check boundaries and practical conclusions

The confirmed findings above are traced to the official documents that own their contracts; they do not rely on previous audit ledgers as proof. Other consequential lifecycle/contract areas inspected included the [App Runner availability change](https://docs.aws.amazon.com/apprunner/latest/dg/apprunner-availability-change.html), [Macie job management](https://docs.aws.amazon.com/macie/latest/user/discovery-jobs-manage.html), and the concrete API contracts linked by the reviewed notes. The current restricted App Runner workflow and Macie status-change workflow are appropriate; remaining Macie wording is ambiguous, not a demonstrated nonexistent command.

The restored notes generally contain service-specific comparisons, concrete request/query/schema examples, operational failure interpretation and bounded exercises. Some are deliberately prerequisite-based runbooks, not copy/paste provisioning packages. That is acceptable where the prerequisites and expected evidence are named. No live AWS execution, full deployment, negative security experiment, billing verification, or test/build result is claimed by this review.
